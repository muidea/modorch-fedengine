# 数据源与虚拟数据库组织调整

状态：代码已接通结构化连接、实例发现、逐目标登记/激活、自动虚拟库、贡献合并、权限路由和 Web 核对流程。部署实例需单独切换；当前存储版本为 7，不迁移旧版本。本文记录现行组织契约和实现边界。

## 已确认的组织规则

对外以 PostgreSQL server 提供 `database → schema → table/view` 三层目录。数据源是连接和管理登记，不能直接等同于唯一对外数据库；数据源登记与虚拟库允许多对一。

- 添加数据源时允许指定源数据库，也允许只指定数据库实例，自动枚举该实例下可管理的数据库。
- 添加时可以定义对外虚拟数据库名，明确区分“源数据库名”和“虚拟数据库名”。
- PostgreSQL 实例枚举出多个源数据库时，每个源数据库对应独立虚拟库，自动生成名称并允许逐项修改。源数据库中的 Schema 保持原名。
- MySQL 这类 `database → table` 产品，每个原生 database 独立映射为虚拟库，并保留同名 Schema；同一连接登记发现多个数据库时，也逐库命名，不合成一个虚拟库。
- 多个数据源指向同一实例的同一个源数据库时，必须合并到同一虚拟库下，其有效纳管范围汇合；不能因登记 ID、显示名称、账号或凭据引用不同而重复生成库。
- 不同实例上的同名源数据库不自动合并。不同 PostgreSQL 源数据库保持独立虚拟库，不通过本轮自动组织合成一个跨源库。
- 系统库默认不纳管、不展示，内部管理库始终不公开。

示例：

| 来源登记 | 原生目标 | 对外组织示例 |
|---|---|---|
| insight_demo | PG `192.168.235.50:5432/lwltest`，范围 insight_demo | `pg_lwltest.insight_demo.*` |
| PostgreSQL17 | 同一 PG `192.168.235.50:5432/lwltest`，范围 public | 合并为 `pg_lwltest.public.*` |
| PostgreSQL12 | PG `192.168.235.50:5433/lwltest`，范围 public | 独立为 `pg12_lwltest.public.*` |
| MySQL8 | MySQL `192.168.235.50:3307`，范围 LWLTEST | `mysql8.LWLTEST.*` |
| MySQL 实例登记 | 同一 MySQL 实例发现 app、sales | 分别为 `mysql_app.app.*`、`mysql_sales.sales.*` |

名称均为示例，实际由添加流程填写或逐项修改。源身份不能通过虚拟库名反推。

## 身份与合并

分离三个层次：连接登记 `SourceConnection`、原生数据库目标 `RemoteDatabase`、对外虚拟数据库 `VirtualDatabase`。原生目标以规范化键标识，与贡献登记的 incarnation 分离；自动 Schema 和关系 OID 不依赖贡献来源或发现顺序。当前对外名称建立后不可在线改名。

原生数据库去重键为产品/协议身份、规范化实例端点和源数据库精确名称。主机名大小写、明确的默认端口等进行确定性规范化；不通过临时 DNS 解析、相同 IP 或同名库猜测两个连接为同一实例。连接别名、代理、多主入口确需视为同一实例时应显式关联实例身份，不能自动推断。凭据和密码不参与去重键，不写入公开目标标识。数据库名保留来源产品实际大小写语义，不统一转成小写。

PostgreSQL 与 MySQL 均按每个 RemoteDatabase 绑定一个独立的自动虚拟库；同一连接登记可对应多个虚拟库。PG 保留原 Schema，MySQL 保留源库名作为该虚拟库内的 Schema。后续登记命中已有目标时复用已有虚拟库，避免重复映射。

首次建立目标时保存自定义虚拟库名。后续登记命中该目标时，添加页面展示“合并到已有数据库”，自动带出已有名称；不能用另一个名称创建第二份同源库。当前不提供已建立自动库的在线改名；添加阶段支持逐项修改未建立目标的名称。对外名称重名但原生目标不同，返回明确冲突，要求修改名称，不依据同名自动合并，也不静默加后缀后发布。

合并后的 Schema 范围来自各登记已生效绑定的并集。相同 Schema/关系只展示一次，每个关系保留其来源登记集合和实际查询路由。移除一个登记只移除它贡献的范围，其他登记仍贡献的对象与库身份保留；删除最后一个贡献也不执行任何来源 DROP。账号同名登录库的业务范围应显式配置，不默认汇集所有来源；PG 未指定数据库时仍遵循登录账号同名库规则。

合并不授予额外权限。数据读取和执行路由必须同时满足 FedEngine 既有授权及实际来源连接能力；目录中描述对象存在不授予其数据权限；不能借由另一个登记的凭据绕过源授权。相同关系有多个贡献时，明确选择一个有权执行的路由及其事实快照；元数据冲突需明确标记，不能按刷新先后互相覆盖。来源表达式和约束事实仍保留来源语义，不声明为本地强制约束。

## 添加与发现交互

1. 填写产品类型、实例端点、凭据引用，以及可选源数据库。连接参数与目标数据库分开表达，不用字符串替换方式改写含密码的 DSN。
2. 填写对外虚拟库名；实例多库模式先提供名称生成前缀，发现后显示可逐项编辑的映射列表。
3. 探测并枚举：PG 展示源数据库及其中 Schema；MySQL 展示源 database 将映射成的 Schema。展示已有虚拟库合并命中、新目标、不可用/无权限及被排除系统库。
4. 核对纳管范围与对外名称，再提交受管异步激活。发现不等于成功发布，部分数据库失败要按目标分别报告，不能声称全部成功。
5. 虚拟库列表汇总关联来源数量和来源数据库；点击库名进入现有对象浏览/SQL 调试。来源与状态页可查看各对象贡献来源和当前执行路由。

实例发现和元数据刷新分离。首次实例添加枚举所有当前可管理数据库；后续“发现数据库”更新候选与差异，已纳管数据库按既有刷新路径处理。新增数据库不会因一次普通目录刷新被静默纳管。上述第 3–4 步沿用现有先核对、再激活的管理交互。

PG 枚举需通过可连接的引导数据库访问 pg_database，过滤模板、禁止连接及系统保留库，并逐库核验连接和元数据权限。引导库是采集连接参数，不更改对外 PG 登录默认库行为。MySQL 枚举使用当前凭据可见范围，排除 mysql、information_schema、performance_schema、sys，逐目标验证可采集性。列出名称不代表具备可查询权限；无权或不可用的数据库保留明确发现状态，不自动激活。空数据库和空 Schema 仍可作为有效目录节点。

## 代码收口顺序

1. **领域及持久化**：拆开登记、实例、原生库和虚拟库关系，建立目标去重、贡献来源与稳定身份；不新增历史格式兼容、迁移链或双模型运行。
2. **连接与枚举**：结构化实例连接参数、引导库和目标库，新增数据库发现结果与逐目标状态；PG 单库连接、MySQL 各 database 连接复用当前执行适配。
3. **管理编排**：按目标分配采集预算、队列和并发，命中目标复用身份；登记/激活/停用/删除均明确其贡献范围。幂等键、CAS、故障恢复及真实租约排空继续生效，不在长屏障内枚举整个实例。
4. **目录发布**：PG 来源 public 直接作为该虚拟库的 public，不与自动创建的空 public 冲突；MySQL 源库名成为 Schema。目录头、映射和查询注册表按已生效目标原子发布，页间快照变化继续拒绝拼接。
5. **查询及权限**：PG 登录、pg_database、pg_namespace、information_schema、绑定、Prepared 失效、owner/CONNECT、默认 search_path 统一使用新身份和有效范围。业务查询仍使用同一协调器，不开放跨库旁路。
6. **API 与 Web**：添加表单提供源库可选和对外库名，接通发现列表、逐项改名、合并提示及部分失败；虚拟库列表、对象来源和 SQL 上下文使用新组织关系。
7. **验证**：对照 DBeaver/JDBC/Web 实测目录与登录；覆盖 PG 两个登记同库不同 Schema 合并、重叠范围去重、多个源库独立命名、MySQL 多库独立命名、多账号权限、重名冲突、发现部分失败、空库、系统隐藏、移除贡献、重启身份、快照与取消排空，以及多目标共享资源上限。

当前运行实例的登记和业务数据不得为适配新模型被直接清空。实现阶段先确定新模型存储版本，部署前正常备份；需要重新登记的开发实例使用独立状态路径及显式重建步骤，不引入历史迁移或覆盖现有实例。

## 当前实现与边界

- `SourceConnection` 是实例发现输入。每个被明确选择的原生数据库登记为独立受管执行目标；持久化 revision 中的 `organization` 保存连接登记 ID、实例、源库、虚拟库、owner/CONNECT。连接登记和原生目标的索引由这些权威记录派生，不维护另一套可独立修改的副本。Web 为目标生成确定性子 ID 和内部执行别名；对外只展示自动虚拟库，内部执行别名不能登录。
- 自动库由已生效目标的快照与范围生成，在现有准备事务中与注册表原子发布。相同 Schema 的贡献共享 Schema OID，PG 关系身份使用原生 relation ID，MySQL 默认按名称保留身份；Strict 模式下原生目标共享不确定性 epoch，任一贡献的严格生命周期重置会统一刷新该目标的投影身份并使 Prepared 失效，单纯移除贡献不会触发重置。停用最后一个贡献保留空库身份；删除最后一个已生效登记移除自动库，均不执行远端 DROP。
- PostgreSQL 关系采集检查来源账号的 Schema USAGE 和表级 SELECT；列级授权不扩展为整表可查询。FedEngine grant 可以引用具体目标 ID，或引用连接登记 ID 授权该登记的目标集合。执行前仍检查实际目标授权。系统库、内部库和禁止连接的目标不会被 Web 激活。
- 重叠关系的 pg_catalog 存在描述按已采集来源 ID 顺序去重，执行路由按有 SELECT 授权的来源 ID 顺序选择。information_schema 对非 owner 按已授权贡献去重。浏览器返回所有可见贡献来源；原生 ID、表种类、列结构、默认值、约束、索引、备注或视图定义不一致时标记 `metadata_conflict`，本地 OID、扫描时间及统计计数差异不视为定义冲突。冲突采用确定性来源，不按刷新先后覆盖；不自动重试到另一份凭据。
- 发现任务为只读、进程内结果，使用 UUID/参数摘要重放检查，结果保留 300 秒；重启需重新发现。激活沿用持久化幂等操作、CAS、恢复和实际排空。发现与源操作共享队列、并发和内存许可；最多保留 16 个发现任务、每实例枚举最多 128 个库、每库枚举最多 1024 个 Schema。超过边界明确失败，允许指定单库缩小范围。
- 自动库每库最多 1024 条 Schema 贡献、有效虚拟库最多 256、受管执行目标最多 128。Web 逐目标登记/激活并显示各自结果；部分失败不撤销其他已成功目标，也不声称整批成功。页面网络结果不明时保留原幂等请求；新增目标始终需核对后明确激活。
- 手工业务库继续用于明确配置的账号同名入口等业务范围；高级执行目标 API 仍可用于显式手工映射。Web 新增数据源默认使用自动组织流程。普通元数据刷新不进行实例枚举，不增加新库或新 Schema 绑定。自动库的组织范围通过来源登记调整，手工映射编辑器不能覆盖自动库。
- 凭据 JSON 与原生目标分离，PG 使用 libpq 单引号转义，MySQL 使用扩展要求的双引号转义，不改写完整 DSN。具体 API 与凭据格式见 [管理 API](management-api.md)。
